1. Visão geral — dois subsistemas desacoplados

A Factory carrega o custo de compilação (horas); o Assembler apenas seleciona binários prontos (segundos). O binhost é a fronteira entre eles.

Factory

Compilação pesada e lenta. Produz binpkgs em variações de USE (multi-instance), publicados por arch.

Binhost

Grafo de nós (CPV, USE) — não um array. Dois pools: build-pool (com transientes) e publish-pool (só finais).

Assembler

Quase instantâneo. --usepkgonly instala binário pronto e monta a ISO. Imune a ciclo.

2. Fluxo de release semanal (cron: domingo 00:00)

A decisão crítica é toolchain-bump: semana normal reusa o tronco (delta rápido); bump de toolchain recria tudo limpo (--emptytree), sem resíduo.

A reprodutibilidade perseguida é de entrada (mesmo input → mesmo conjunto de pacotes), não bit-a-bit. O -march=native é banido; cada arch usa -march explícito.

3. Package Factory — build em fases

Cada fase é um emerge próprio, ordenado, com o /etc/portage do flavor já aplicado. A ordenação resolve deterministicamente os ciclos de pacotes grandes.

4. Quebra de dependência circular (use_break)

Ciclo real medido por pretend-resolve: libsdl2 → pipewire → ffmpeg → libsdl2. A quebra é curada manualmente por flavor: compila com a USE desligada, depois religa.

flowchart LR
    PR["pretend-resolve.sh
(emerge --pretend)"]:::tool --> CUR["curadoria manual
do use_break na recipe"]:::dec
    CUR --> BP["BREAK-PASS
ffmpeg#91;-sdl#93;
(binpkg transiente)"]:::trans
    BP --> SP["SETTLE-PASS
ffmpeg#91;sdl#93; final
(parceiro do ciclo ja presente)"]:::art
    SP --> GC{"GC ciente de USE"}:::dec
    GC -->|"transiente"| PODA["podar (só build-pool)"]:::stop
    GC -->|"final"| KEEP["publicar (publish-pool)"]:::art

O binpkg transiente existe só para quebrar o ciclo e nunca chega à ISO. O binhost.gc() distingue variante-de-flavor (manter todas), versão antiga (keep-N) e transiente (podar).

5. Fork-point & particionamento do binhost

As fases iniciais dependem só do init. O fork por desktop ocorre tarde — o tronco compila uma vez por init; só a fase de desktop ramifica.

Por arch (físico)

Obrigatório: binpkg znver5 (AVX-512) não roda em v3. Um tree por arch.

Por USE (lógico)

multi-instance + BUILD_ID absorve as variações de flavor/init dentro de cada arch.

Cache compartilhado

ccache/sccache são keyed por flags → seguros entre flavors sem violar a pureza do container.

6. ISO Assembler — imune a ciclo

Ciclo é fenômeno de build-time. O Assembler navega o grafo multi-instance e extrai a fatia do flavor pela USE final — toda a complexidade fica na Factory.

flowchart TD
    SEED["container seeda stage3"]:::seed --> RES["resolve USE final do flavor"]:::proc
    RES --> MATCH{"match multi-instance
no binhost"}:::dec
    MATCH -->|"poppler#91;qt6#93;"| KDE["ISO KDE"]:::art
    MATCH -->|"poppler#91;gtk#93;"| GN["ISO GNOME / XFCE"]:::art
    MATCH -->|"sem DE"| MIN["ISO minimal"]:::art
    KDE --> SQ
    GN --> SQ
    MIN --> SQ["mksquashfs zstd -19
(rootfs read-only)"]:::proc
    SQ --> DR["dracut dmsquash-live
(overlayfs em RAM)"]:::proc
    DR --> ISO["grub-mkrescue / xorriso
→ ISO híbrida BIOS+UEFI"]:::art

Requisito de consistência: a USE final do settle-pass da Factory deve ser idêntica à USE que o Assembler resolve — senão --usepkgonly falha sem match.

7. Matriz de eixos componíveis

Uma release é a tupla base + arch + flavor + init, resolvida por deep-merge. Os eixos não se multiplicam de forma ingênua (desktop ≈ flavor).
